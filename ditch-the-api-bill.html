—— The problem

Every team wants LLMs. Each easy way in has a catch.

Call a cloud API

  • Prompts and data leave your network
  • Pay per token: the bill grows with every user
  • Hard to govern who uses which model, and how much

Run it yourself

  • GPUs are scarce and expensive
  • One team per GPU leaves most of it idle
  • Every team rebuilds serving, access and quotas

Clicks on this slide

  1. Arrive: the cloud API. Every prompt crosses out of your network, and the bill ticks up with every one.
  2. Click: running it yourself, one GPU per team. Each sits mostly idle, a few percent busy, yet each costs a whole GPU.

—— What we want

One front door for any model, with self-service keys

One front door for our own models and cloud APIs. Developers create their own keys, scoped to their subscription and revocable at once. Next: what it takes to build it.

Clicks on this slide

  1. Arrive: who calls is not only people. User groups, services and agents each hold their own API key, created self-service and scoped to a subscription. All of them come through one front door to one shared pool of GPUs inside your network, so the pool runs busy instead of GPUs sitting idle.
  2. Click: the same door, the same keys, reach cloud APIs too, but only for the requests you choose to send out. Everything else stays inside, and the bill grows slowly.
  3. Click: the agent misbehaves, so its key is revoked. Its very next request is refused at the door with 401; everyone else carries on.
  4. Click: the sentence to remember. The next slide shows the stack that makes this work.

Illustrative, like the previous slide: the figures are not measurements.

—— The engine · vLLM

vLLM keeps one GPU busy with dozens of requests at once

  1. 1

    Continuous batching

    Requests join and leave the batch at every step: nobody waits for the slowest answer, and the GPU never idles.

  2. 2

    PagedAttention: KV cache in pages

    Every token in flight keeps its attention state, the KV cache, in GPU memory. vLLM stores it in small pages like virtual memory, so little is wasted and more requests fit. When pages run out, requests wait.

  3. 3

    Prefix caching

    Prompts that start the same, such as a shared document, reuse pages already computed instead of reading it again.

Clicks on this slide

  1. Arrive: static batching runs alone. Four requests start together; short ones finish and their slot sits idle (hatched) until the longest is done.
  2. Click: continuous batching runs under it on the same requests. A finished slot is refilled at once: more requests done, the GPU busy nearly all the time.
  3. Click: PagedAttention, the KV cache as pages of GPU memory. Requests take pages anywhere free; a long document arrives and fills it past 80%, and new requests have to wait. That is exactly the autoscaler's trigger in scene 3.
  4. Click: prefix caching. Request A reads the whole shared document; B, C and D find it already in cache and only read their own question, so their first token comes almost at once.
  5. Click: the rest of what vLLM does, across the whole slide (the animation steps aside). Next click goes to llm-d.

The small print, if anyone asks

  • KV cache (PagedAttention): attention state stored in fixed-size pages, like virtual memory, so little GPU memory is wasted and more requests fit.
  • Speculative decoding: a small draft model (or n-gram guess) proposes several tokens, the big model checks them in one pass; faster answers, same output.
  • Chunked prefill: long prompts are read in slices interleaved with generation, so one big document does not stall everyone else.
  • Hardware: upstream vLLM runs on NVIDIA and AMD GPUs, Intel Gaudi accelerators and GPUs, Google TPUs and x86/Arm CPUs. Check the Red Hat AI Inference Server support matrix for what is supported in product.

Links: vLLM documentation · PagedAttention paper (Kwon et al., 2023) · Red Hat AI Inference Server

—— The scheduler · llm-d

Round-robin is the wrong way to share LLM replicas

Requests are not alike. A one-line question and a 2,000-token document cost the GPU very different amounts of work.

Where it lands matters. The replica that already holds the start of your prompt answers it several times faster.

Busy is invisible from outside. Only the server's own queue and memory say whether it can take more.

llm-d reads each replica's queue live and remembers what each one has cached, so prompts that share a document stay on the replica that has it, and new work goes to the one with room.

Clicks on this slide

  1. Arrive: round-robin. Two shared documents, A and B; each replica can keep one cached (#1 has A, #2 has B). Round-robin alternates blindly: half the questions land where their document is not, the replica re-reads 2,000 tokens and evicts the other document. Cache hits collapse and long documents pile up behind each other.
  2. Click: llm-d. For every request it scores both replicas (queue ×4, prefix-cache match ×3, KV-cache use ×2, least recently used ×2) and the higher total wins: A questions go to #1, B to #2, new documents to whichever has room. Nearly every shared question is a cache hit. Queue and KV use come live from each vLLM's metrics; the cache contents llm-d infers: it fingerprints every prompt it routes (hashes of fixed-size chunks) and remembers which replica got them. A precise mode, where vLLM reports every cache block it stores or evicts, also exists; the demo uses the default, estimated one.
  3. Click: the takeaway line. Next click goes to Models-as-a-Service.

The weights are the ones configured in the demo. Measured on the demo cluster: shared-document prompts hit the cache about 96% of the time on Qwen3; brand-new 2,000-token prompts split 137 / 131 between two replicas in one minute.

—— The front door · Models-as-a-Service

Models-as-a-Service: one front door, with the rules built in

Route by model

Meter usage

Easy to consume

One OpenAI-compatible endpoint and one credential for every model, self-hosted or cloud.

Cost control

A token budget per subscription, tighter on pay-per-token cloud models. Every token is metered and attributed.

Privacy by placement

Prompts to self-hosted models never leave the cluster. Cloud APIs get only what you route there, and the gateway holds their keys.
